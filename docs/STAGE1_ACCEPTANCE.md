# Приёмка этапа 1

Дата проверки: 13 ноября 2026 года.

Реализация находится в рабочей папке. Клиентские, серверные и интеграционные
SQL-проверки успешны. Постоянное развёртывание серверных изменений и проверка
реального входа через развёрнутую функцию остаются открытыми.

## Выполненные проверки

- TypeScript приложения и тестов: успешно (`tsc --noEmit`, `tsc --noEmit -p tests`).
- ESLint: успешно.
- Prettier: все файлы соответствуют форматированию.
- Jest: 23 набора, 199 тестов успешно.
- Deno: типизация четырёх точек входа успешна, 38 тестов успешно.

Jest и Deno запускались вне песочницы после ошибок доступа к временным файлам
и запрета запуска Deno. Для Jest использовались `TEMP` и `TMP` внутри
`.tools/tmp`; переменные задавались только для процесса проверки.

Дополнительно выполнены проверки реальной PostgreSQL через Management API:

- Подготовленная миграция и `supabase/tests/rls.sql` выполнены в единой
  транзакции с откатом: изоляция A/B, клиентские ограничения доступа,
  ограничения данных и каскадное удаление успешны.
- Для конкуренции создана отдельная закрытая схема с уникальным именем.
  SQL миграции использован с заменой только квалификатора схемы `public.`.
  Два одновременных HTTP-запроса выполнили погашение под `service_role`;
  разные `pg_backend_pid()` подтвердили независимые соединения PostgreSQL.
  После вызова транзакции удерживались ещё секунду через `pg_sleep(1)`.
  Получены результаты `true` и `false`, повтор и истёкший код дали `false`,
  сохранена ровно одна запись.
- Тестовая схема удалена. Проверено отсутствие тестовых аккаунтов и таблицы
  погашений в `public` после отката. Пользовательские данные не менялись.

Это проверка RPC и RLS; выпуск двух реальных сессий через развёрнутую Edge
Function не проверялся. Локальный `scripts/test-redemption.py` отдельно не
запускался: Docker и psql отсутствуют; его сценарии проверены через API.

## Доступ к рабочему Supabase

Проект из `app.json`: `ywlbltxdagjlhevftkst`.

- Плагин Supabase установлен и включён по ответу управления плагинами.
- Его `list_projects` и `execute_sql` возвращают `Unknown tool`.
- Прежний локальный токен возвращал HTTP 401. После замены токена запросы
  Management API на чтение успешны (HTTP 201).
- Dashboard во встроенном браузере не загрузился: `ERR_CONNECTION_RESET`.

Прочитаны история миграций, таблицы, политики и права на колонки:

- `users`, `games`, `play_sessions` имеют включённый RLS и политики владельца.
- Добавление и изменение игр разрешены `authenticated` на уровне колонок,
  как в локальной схеме; только табличные ACL этих разрешений не показывают.
- История содержит `20261101221734 rawg_checked_at` и
  `20261101225242 last_played_at`. Начальная схема существует, хотя отдельной
  записи начальной миграции в полученной истории нет.
- `public.steam_auth_redemptions` и `public.claim_steam_auth_code` отсутствуют.
- Фиксированные UUID двух тестовых аккаунтов не заняты.

При повторной проверке запись работает: запрос с `read_only: false` выполняется
под `postgres`, `transaction_read_only=off`; создание временной таблицы и запись
в неё успешны с откатом. Запросы с `read_only: true` выполняются под
`supabase_read_only_user`; такая роль в ответе запроса только на чтение сама
по себе не доказывает ограничения токена. Ранее пробный запуск возвращал
SQLSTATE `25006`; при последней проверке эта блокировка не воспроизводится.

Для последующего применения миграции через специальный endpoint требуется
`database_migrations_write`; доступ к этому endpoint отдельно не проверялся.
Развёрнутая версия `steam-auth` пока не проверена.

## Что осталось для приёмки

1. Постоянно развернуть миграцию, затем `steam-auth`, затем клиент в порядке
   из `supabase/README.md`. Тесты выше не сохраняли миграцию в рабочем `public`.
2. Проверить штатный Steam-вход через обновлённую развёрнутую функцию.
3. Получить зелёный CI, включая воспроизводимые локальные SQL-проверки.

Порядок запуска интеграционных тестов и ограничения среды описаны в
[Supabase README](../supabase/README.md).
