# Технический аудит PlayNow

Дата: 13 ноября 2026 года.

PlayNow помогает выбрать игру из Steam-библиотеки по контексту. В репозитории
реализован основной путь пользователя, но перед публичным релизом нужно укрепить
обмен кодов входа, синхронизацию и проверки на реальных устройствах. Приоритет
разработки — надёжность этого пути, затем качество рекомендаций.

## Устройство проекта

- Клиент: Expo SDK 58, React Native, TypeScript strict, React Navigation native stack.
- Состояние: Zustand для сессии, TanStack Query для загрузок и общего кэша.
- Данные: Supabase Auth и Postgres с RLS; Edge Functions на Deno.
- Интеграции: Steam OpenID и библиотека игр; RAWG для жанров и обложек.
- На устройстве: SecureStore для мобильной сессии, AsyncStorage для библиотеки
  и отложенных игр. Веб-сессия использует localStorage.
- Реализованы вход, импорт, поиск и фильтры, ручное добавление, подбор,
  откладывание, переход в Steam, настройки и удаление аккаунта.

Основа поддерживаемая: код разделён по функциям продукта, сервисы допускают
подмену зависимостей, ответы внешних API валидируются. Steam ID берётся из
`app_metadata`, серверные ключи не входят в публичный конфиг. Таблицы разделяют
данные пользователей через RLS. Эти решения следует сохранить.

## Приоритеты до релиза

### P1 Повторный обмен кода входа

`supabase/functions/steam-auth/openid.ts` проверяет HMAC, PKCE и срок 120 секунд.
`steam-auth/index.ts` после проверки выпускает сессию без атомарной отметки об
использовании кода. Та же пара code/verifier допускает повторный обмен до истечения
срока. PKCE защищает перехваченный код без verifier, но одноразовость не обеспечивает.

Следующий шаг: хранить факт погашения на сервере и атомарно отклонять повтор,
включая запросы к разным экземплярам функции. Критерий готовности: два параллельных
обмена одной пары дают ровно одну сессию; тест проходит на локальном Supabase.
Изменение требует миграции и согласованного развёртывания серверной функции.

### P1 Надёжность синхронизации библиотеки

`steam-library/index.ts` читает таблицу одним `select` без пагинации. При превышении
лимита ответа база вернёт только часть библиотеки. По документации Supabase
[стандартный предел составляет 1000 строк](https://supabase.com/docs/reference/javascript/select).
Нужны страницы со стабильной сортировкой и тест библиотеки больше лимита.

`useBacklog.ts` запускает обогащение отдельно от импорта, а сетевые операции не
используют сигнал отмены Query. Выход очищает кэш, но незавершённая операция может
позднее записать его снова. Нужны отмена запросов и защита записи от устаревшей
сессии. Проверка: выйти или сменить аккаунт во время загрузки и обогащения;
после завершения старых запросов кэш вышедшего пользователя не восстанавливается.

### P2 Качество подбора

`picker/utils/contexts.ts` и `pickGame.ts` для «У меня 30 минут» фильтруют игры по
суммарному времени из Steam: меньше 60 минут за всё время. Это не оценка длительности
одной сессии. Нужно уточнить обещание в интерфейсе либо добавить отдельные данные
о длительности. Сейчас давно любимая короткая игра может быть исключена.

Игры без распознанного жанра не проходят ни один контекст. `runEnrichment` ограничен
15 партиями по максимум 80 игр, а при медленных API обрабатывается меньше. Нужны
явное состояние неполных метаданных и возобновление обработки, чтобы пустой подбор
не выглядел как отсутствие подходящих игр в библиотеке.

### P2 Полнота удаления и срок откладывания

`useDeleteAccount.ts` очищает библиотеку и Query, но не вызывает `BlacklistService.clear`:
локальные отложенные игры остаются после удаления аккаунта. Следует очищать их
с отдельной проверкой ошибки хранилища.

`useBlacklist.ts` задаёт `staleTime: Infinity`. Просроченные записи удаляются только
при чтении сервиса, поэтому в открытом приложении срок может фактически превышать
7 дней. Нужны повторное чтение или таймер ближайшего истечения.

### P2 Проверки релизного сценария

Unit-тесты в основном покрывают чистые утилиты; нет автоматического полного пути
Steam → импорт → обогащение → подбор → выход и смена аккаунта. SQL-проверка
`supabase/tests/rls.sql` также не входит в CI. Нужны интеграционные проверки Auth/RLS
и проверка основной цепочки на Android и iOS, включая оффлайн и возврат из браузера.
Наличие EAS-конфига и скриншотов не заменяет проверку текущей сборки.

## Исправлено в ходе аудита

1. Для RAWG-обогащения добавлен отдельный таймаут 90 секунд. Сервер начинает
   обработку игр в течение 25 секунд, последняя игра может потребовать ещё до
   30 секунд внешних запросов плюс обращения к Auth и БД. Прежние 10 секунд могли
   оборвать нормальную партию. Остальные запросы сохраняют лимит 10 секунд.
2. HTTP-обёртка снимает обработчик внешней отмены и таймер при завершении.
   Добавлены три регрессионных теста на сроки, отмену и очистку ресурсов.
3. В CI добавлена отдельная задача Deno: проверка четырёх серверных точек входа
   и тестов с `--frozen` для сохранения lock-файла.
4. Jest исключает `.tools` из поиска модулей: устранена коллизия имени пакета
   с локальным служебным каталогом.

## Проверки и границы результата

- TypeScript, ESLint и проверка форматирования Prettier прошли после исправлений.
- После исправлений Jest: 117 тестов, 7 наборов, все прошли.
- Deno: проверка четырёх точек входа и 36 тестов прошла, включая команды нового CI.
- `expo install --check` использовал локальную карту SDK и не нашёл несовместимости;
  актуальная сетевая проверка версий недоступна в этой среде.
- Текущий аудит не подтверждает состояние развёрнутой базы, фактические настройки
  серверных секретов или прохождение сценария Steam на устройстве.
- Рабочее дерево уже содержало незакоммиченные изменения; они сохранены.
  Автоматического деплоя, публикации и коммита в ходе аудита нет.

## Порядок дальнейшей разработки

1. Закрыть повторный обмен кода с тестом параллельных запросов.
2. Добавить пагинацию и отмену загрузок при выходе, проверить большие библиотеки.
3. Исправить очистку отложенных игр, их истечение и возобновление обогащения.
4. Включить RLS и интеграционные сценарии в CI, проверить сборку на устройствах.
5. Уточнить критерии контекстов и развивать подбор по измеримым сценариям.

Каждое изменение завершать typecheck, lint и подходящими регрессионными тестами.
Перед релизом отдельно фиксировать версию сборки, применённые миграции и результат
проверки пользовательского пути. `docs/FIXES.md` содержит исторические результаты;
его статусы нельзя считать подтверждением состояния текущего дерева.
