# Supabase

## Схема

| Таблица         | Назначение                                          | Доступ клиента (RLS)                      |
| --------------- | --------------------------------------------------- | ----------------------------------------- |
| `users`         | профиль: `id` = `auth.users.id`, `steam_id`         | только чтение своей строки                |
| `games`         | бэклог пользователя, уникален по `(user_id, appid)` | CRUD своих строк, `user_id` менять нельзя |
| `play_sessions` | история запусков игр                                | CRUD своих строк, только на свои игры     |

`users` создаёт и обновляет только Edge Function под `service_role` после проверки входа через Steam (этап 4).
Иначе клиент мог бы подставить чужой `steam_id` и получить чужую библиотеку.

## Применить миграции к проекту

```bash
npx supabase login
npx supabase link --project-ref <ref из URL проекта>
npx supabase db push
```

## Проверить RLS

Против локального Supabase (`npx supabase start`, нужен Docker):

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" -v ON_ERROR_STOP=1 -f supabase/tests/rls.sql
```

Скрипт работает в транзакции с откатом. Любая проваленная проверка останавливает его с `FAIL: ...`.

## Этап 1: одноразовый вход и изоляция аккаунта

Порядок развёртывания: сначала применить миграцию
`20261113000000_steam_auth_redemptions.sql`, затем развернуть `steam-auth`,
после этого выпустить клиент. Обновлённая функция требует RPC
`claim_steam_auth_code`: без миграции обмен завершится ошибкой сервера, сессия
не будет выдана. Откат к прежней функции вернёт возможность повторного обмена.

RPC погашает код атомарным `INSERT ... ON CONFLICT` в общей базе до выпуска
сессии. Повтор и параллельный обмен отклоняются. Если выпуск сессии после
погашения не удался, нужно начать вход заново. При недоступной базе функция
не выдаёт сессию. Старые подписанные коды совместимы в пределах прежнего TTL;
новые дополнительно содержат случайный идентификатор. Хранятся только хэши
подписанных данных и срок действия, без SteamID, токенов и PKCE verifier.
Просроченные записи очищаются следующим погашением.

Формат существующего локального кэша не меняется. Выход, отзыв сессии и смена
аккаунта отменяют запросы, удаляют кэш библиотеки и блокируют запись поздних
результатов прежней сессии. Отложенные игры сохраняются при обычном выходе.
Удаление аккаунта очищает все его ключи `playnow:<feature>:<version>:<steamId>`,
включая отложенные игры; новые аккаунтные данные должны следовать этому формату
и использовать очередь `accountScope`. Тема `quaeso:theme` остаётся настройкой
устройства. Нельзя использовать общий `AsyncStorage.clear()`.

Воспроизводимая интеграционная проверка (Docker, Supabase CLI, psql, Python 3):

```bash
npx supabase db start
npx supabase migration up
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" -v ON_ERROR_STOP=1 -f supabase/tests/rls.sql
python scripts/test-redemption.py
```

`rls.sql` проверяет доступ в обе стороны между A и B, запрет клиентского
погашения кодов и каскадное удаление с сохранением второго аккаунта.
`test-redemption.py` открывает два независимых подключения к локальной базе
и проверяет один успех, один отказ, повтор и истёкший код. Тест удаляет
созданную им запись; адрес локальной базы зафиксирован в скрипте.
Обе проверки включены в job `database` в CI.

Проверка 13 ноября 2026: 199 клиентских и 38 Deno-тестов успешны;
типизация, lint и форматирование проходят. Через Management API успешно
выполнены пробная миграция и RLS-тесты в транзакции с откатом. Параллельное
погашение проверено на двух независимых PostgreSQL-соединениях в отдельной
закрытой тестовой схеме: один успех, один отказ; повтор и истёкший код отклонены.
Тестовая схема удалена, отсутствие тестовых аккаунтов подтверждено.
Постоянная миграция и обновлённая функция в рабочем проекте пока не развёрнуты;
реальный вход через обновлённую развёрнутую функцию ещё требует проверки.
В текущей среде нет Docker и psql, локальный Python-скрипт отдельно не запускался.
Подробности и оставшиеся условия приёмки: [STAGE1_ACCEPTANCE.md](../docs/STAGE1_ACCEPTANCE.md).

## Этап 2: полная библиотека и метаданные

Развёртывание: применить миграцию `20261113092721_game_genre_overrides.sql`,
затем обновить `steam-library` и `rawg-enrich`, затем выпустить клиент.
Миграция добавляет только nullable-колонку `games.genres_override` и право
обновления этой колонки для `authenticated`. Политики владельца продолжают
действовать. Существующие жанры и кэш версии 1 сохраняются.

`steam-library` читает библиотеку страницами до 500 строк по уникальному
`appid`, используя `appid > cursor` и стабильную сортировку. Чтение продолжается
до пустой страницы, включая случай меньшего серверного лимита. Ошибка страницы
не выдаётся за успешно загруженную неполную библиотеку. В ответ включены ручные
игры и число строк с `rawg_checked_at is null` в `remaining`.

Клиент отдельно показывает импорт библиотеки и обработку метаданных. Остаток
сохраняется вместе с кэшем; ненулевой остаток означает неполную обработку,
даже если цикл остановился по лимиту раундов, отсутствию прогресса или сбою
части партии. «Продолжить загрузку жанров» вызывает только `rawg-enrich`;
функция выбирает только ещё не проверенные игры. Подтверждённо обработанные
игры повторно в RAWG не отправляются. Жанры, которые RAWG не распознал,
можно исправить в карточке игры.

Пользовательское исправление хранится отдельно от `genres`, имеет приоритет
при показе и подборе, не записывается импортом и обогащением и не меняет
playtime. `null` возвращает автоматические жанры; пустое исправление запрещено.
Редактирование требует сети, записывает только подтверждённый аккаунт и не
показывает успех при ошибке сервера. Офлайн остаются список и исправленные
жанры из кэша с датой последнего импорта.

Дополнительная интеграционная проверка после запуска локального Supabase:

```bash
node scripts/test-library.mjs
```

Требуются Node 24 и `psql`. Скрипт использует настоящий серверный helper
пагинации, фиксированный локальный адрес и временную закрытую схему. Проверяет
0, 1, 500 и 1500 строк, одинаковые названия и ручную игру; в конце удаляет
свою схему. Включён в CI вместе с дополненным `rls.sql`.

Проверка на рабочем PostgreSQL через Management API 13 ноября 2026 успешна:
обе подготовленные миграции и `rls.sql` выполнены с откатом; проверены
изменение жанров владельцем, запрет для другого аккаунта и сохранение
исправления после изменения импортируемых полей. Реальный helper также прочёл
наборы 0/1/500/1500 из отдельной закрытой тестовой схемы без пропусков и
дубликатов. Временная схема удалена, постоянная схема приложения не менялась.
Использовался эквивалент `scripts/test-library.mjs` с HTTP-запросами вместо
`psql`, поскольку локальные Docker и psql недоступны.

Постоянное развёртывание и проверка полного импорта с настоящими Steam/RAWG
через обновлённые Edge Functions пока не выполнены. Состояние первого этапа
уточнено в [отчёте приёмки](../docs/STAGE1_ACCEPTANCE.md).

В рабочей истории миграций начальная схема не зарегистрирована отдельной
записью. Перед постоянным развёртыванием нужно сверить историю с существующей
схемой и применить только новые миграции; слепой `db push` всех локальных
файлов может попытаться повторно создать уже существующие таблицы.

Проверка Security Advisors на существующем проекте успешна. Возвращено одно
предупреждение о выключенной [защите паролей от утечек](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
Настройки Auth в рамках этапа 2 не менялись. Проверка отражает рабочую схему;
тестовая миграция была откачена, её права проверены отдельно SQL-тестами.

## Этап 3: статусы и исключения

Перед выпуском клиента применить миграцию
`20261113094802_game_preferences.sql` к уже согласованной схеме. Миграции и
Edge Functions этапов 1–2 по-прежнему разворачиваются в своём порядке; новая
миграция их не заменяет. Без таблицы статусов подбор не игнорирует ограничения
молча: при отсутствии сохранённых данных он блокируется с ошибкой и повтором.

`game_preferences` хранит отдельно от импортируемых данных `progress_status`
(`unspecified`, `not_started`, `playing`, `completed`) и `excluded`. Внешний
ключ `(user_id, appid)` ссылается на игру владельца и удаляет настройки вместе
с игрой или аккаунтом. RLS ограничивает все операции владельцем; идентификатор
пользователя и appid существующей записи нельзя менять. Время Steam никогда
не создаёт статус прохождения.

RPC `set_game_preference` работает как `SECURITY INVOKER`, проверяет ожидаемый
идентификатор пользователя и атомарно изменяет только явно переданные поля.
Поэтому смена статуса не снимает постоянное исключение, а исключение не меняет
статус, жанры и playtime. Импорт Steam и RAWG эту таблицу не записывают.
«Вернуть в подбор» снимает постоянное исключение и возвращает статус
`completed` в `unspecified`; другие явные статусы сохраняются.

После подтверждённой записи показывается сообщение и «Отменить». Отмена
восстанавливает прежние значения только изменённых полей. Неуспешная запись
оставляет прежнее видимое состояние; неуспешную отмену можно повторить.
Изменение серверных признаков требует сети, чтение допускает отдельный кэш
`playnow:preferences:v1:<steamId>`. Удаление аккаунта очищает этот ключ вместе
с остальными данными пользователя, сохраняя тему устройства.

Временное откладывание хранится в прежнем формате blacklist v1 только на этом
устройстве. «До завтра» означает ближайшую полночь по времени устройства,
«На неделю» — семь суток. Запись выполняется последовательно, чтобы параллельные
действия и очистка просроченных записей не теряли другие игры. Ошибка записи
не выдаётся за успешное откладывание и не скрывает игру только в памяти.
Истечение срока обновляет общий кэш по таймеру и при `AppState=active`, в том
числе после сна приложения. Статус, постоянное исключение и откладывание
остаются независимыми; игра участвует в подборе только при отсутствии всех
трёх ограничений. Исключённая игра остаётся доступна в библиотеке.

Дополнительная интеграционная проверка в CI и локальном Supabase:

```bash
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" -v ON_ERROR_STOP=1 -f supabase/tests/preferences.sql
```

На подключённом PostgreSQL 13 ноября 2026 миграция и этот SQL-набор успешно
проверены в транзакции с откатом: RLS A/B, недействительная ожидаемая учётная
запись, ограничения статуса, независимость признаков, сохранение при импортном
upsert и удаление каскадом. В отдельной закрытой временной схеме проверены
два параллельных изменения через разные соединения: итог сохранил и статус
`playing`, и исключение. Временная схема удалена; постоянная схема приложения
не менялась. Полный прогон на физических устройствах и постоянное развёртывание
ещё не выполнены.

## Этап 4: честный и объяснимый подбор

Новой миграции нет. Перед выпуском клиента обновить `steam-library`;
предварительно выполнить условия развёртывания этапов 1–3. Функция добавляет
к каждой игре необязательный признак `steam_imported`, основанный на текущем
ответе Steam о владении. Ручная запись с настоящим appid без подтверждения
владения не получает этот признак. Старые ответы и кэш совместимы: без
подтверждённого источника причины используют нейтральное «время в библиотеке».
Признак сохраняется при обогащении метаданных и ручном исправлении жанров;
новая колонка базы не нужна.

Подбор сначала применяет исключения, затем жанры и режим. «Новое» отдаёт
приоритет явному «Не начинал», «Продолжить» — явному «Играю». Следующая группа
включает только неуказанный статус и соответственно нулевое или положительное
время. Случайный выбор равномерен внутри лучшей доступной группы ещё не
показанных кандидатов, без ограничения топом из десяти. После исчерпания
серии показывается предупреждение; повторения разрешает только явный новый
круг. Накопленное время не используется как оценка длительности сессии.

Режим и контекст хранятся в `playnow:pickerSelection:v1:<steamId>` с очередью
`accountScope` и очищаются при удалении аккаунта. Поздние чтения и записи
предыдущего аккаунта не заменяют текущий выбор. Первый режим — «Новое»;
пустой результат не меняет условия автоматически. Явное действие «Любая игра
без фильтра жанров» сохраняет режим, статусы и все исключения.

В интеграционный `scripts/test-library.mjs` добавлена проверка происхождения:
ручные игры, включая настоящий Steam appid, не получают подтверждение Steam
без соответствующего импорта. Эквивалент через Management API успешно проверен
на наборах 0/1/500/1500 записей в отдельной закрытой схеме; схема удалена.
Регрессионные SQL-проверки миграций и RLS выполнены с откатом.
Постоянное развёртывание функций и проверка на физических устройствах
ещё не выполнены.
